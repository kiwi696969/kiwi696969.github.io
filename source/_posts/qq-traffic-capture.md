## 一、实验条件

想抓一张图，需要的其实就三样东西：

- 一台手机、一台电脑，**连在同一个热点下**
- 电脑装好 Wireshark（以及它的抓包驱动 Npcap）
- 一个十六进制编辑器 —— 这里用 010 Editor，WinHex、HxD、MadEdit 效果都一样

**为什么必须在同一个热点**：抓包只能看到**经过本机网卡**的流量。手机和电脑在同一个局域网里，它们和外部服务器之间的数据才会流经电脑的网卡。如果手机走 4G/5G、电脑走宽带，两条路互不相干，抓一整天也抓不到手机的任何包。

> 顺带一个小细节：截图里电脑拿到的地址是 `172.20.10.x`。这是 iPhone 个人热点的默认网段，看到这个号段就知道，热点是手机开的，电脑是连上去的那一方。

## 二、抓包

### 1. 选对网卡，开始捕获

打开 Wireshark，接口列表里选**正在联网的那块无线网卡**。

容易选错的三个：

- `VMnet1` / `VMnet8` —— 这是 VMware 的虚拟网卡，跟手机没关系
- `Loopback` —— 本机自己跟自己通信
- 蓝牙、VPN 之类的虚拟适配器

分不清哪块在跑流量，就看接口列表右边的**实时流量曲线**：发图的时候哪条曲线在跳，那就是它。双击开始捕获。

### 2. 手机发原图给电脑

![手机端把原图发送到电脑，3.28 MB](/img/httpcap-01.png)

这里有两个细节决定了成败：

**一是必须发「原图」。** 聊天窗口里默认发的是压缩过的缩略图，服务端会重新编码，抓下来虽然也能拼回去，但拿到的不是你拍的那张。要还原，就得让原文件原样过一遍网络。

**二是发之前先看一眼文件大小。** 3.28 MB 这个数字后面有用 —— 它就是你在 Wireshark 里确认"抓对了没有"的依据。

### 3. 停止捕获

进度条走完、状态变成"已下载"，立刻点左上角的红色方块停止。

> ⚠️ **别贪多。** QQ 在后台会持续跑心跳、拉消息、同步联系人，抓十分钟能攒出几十万个包，在里面找一张图基本等于大海捞针。发图前后各留几秒就够，几百个包最舒服。

## 三、从一堆包里找到那张图

在过滤栏输入：

```
http
```

回车。列表会从几十万条瞬间缩到几百条。

![过滤 http 之后，能看到一条标注为 JPEG 的下载请求](/img/httpcap-02.png)

这一步之所以有效，是因为 **QQ 传图片走的是 HTTP 明文**。响应头里带着 `Content-Type: image/jpeg`，Wireshark 认出了这个类型，直接在 Info 列标成 **(JPEG JFIF Image)**。

看截图里那条请求：

```
GET /qqlive/Tjznm3w7sMBmyxjKR5wMUcNCqumbCpK9eOmHlzIyAhR8Nb2sprsvg==?token=...
```

一长串 Base64 风格的路径加一个 token。**不需要理解那串东西是什么**，看 Info 列的类型标注就够了 —— 它是整屏里唯一一条被标成 JPEG 的。

顺便能读出一个事实：图片不是手机直接传给电脑的，而是**手机先上传到腾讯的服务器，电脑再从服务器下载**。所以这条 GET 的目的地址是公网 IP，不是手机的内网地址。

## 四、把整条流导出来

右键那条包 → **追踪流 → HTTP Stream**（选 TCP Stream 也可以）：

![右键 → 追踪 → HTTP Stream](/img/httpcap-03.png)

弹出的窗口里是这条连接上**来回传输的全部原始字节**。左下角"整个对话"显示 **3437 kB** —— 和手机上那个 3.28 MB 基本对得上，到这里可以确认：抓对了。

![追踪流窗口，整个对话 3437 kB，显示方式选原始数据](/img/httpcap-04.png)

窗口底部有两个地方要调：

| 选项 | 值 | 说明 |
|---|---|---|
| 显示 | **原始数据** | 选 ASCII 会把二进制显示成乱码，也别选 C Arrays |
| 另存为 | `111.jpg` | 文件名随便，后缀先按图片的写 |

存下来双击打开 —— **大概率打不开**。这是正常的，下一节解释。

## 五、用 010 Editor 修复文件头

### 为什么打不开

因为你保存的是**整条流**，不是一张图片。文件开头长这样：

```
HTTP/1.1 200 OK
Content-Type: image/jpeg
Content-Length: 3437000
Server: ...
（空行）
ÿØÿà ...        ← 真正的图片从这里才开始
```

看图软件从第一个字节开始按 JPEG 规范解析，读到的是 `H`（0x48），不是 `FF D8`，直接判定"这不是 JPEG"然后放弃。

**`FF D8` 就是 JPEG 的身份证**，后面通常紧跟 `FF E0`（JFIF 标记）。只要把这两个字节之前的所有东西砍掉，剩下的部分就是一整个合法的 JPEG。

### 操作

用 010 Editor 打开 `111.jpg`，`Ctrl + F` 打开查找框：

- **查找类型**：选「十六进制字节」
- **内容**：填 `FFD8`

![在 010 Editor 里按十六进制查找 FFD8](/img/httpcap-05.png)

这里有个容易翻车的点：**`FF D8` 可能命中不止一个**。JPEG 里嵌缩略图、文件尾部还有第二张图，都会额外出现这个组合。**认准最靠前的那个**，它才是主图的起点。

然后看命中的偏移量：

- 如果显示 **`0h`** → 文件开头就是图片，说明没混进多余数据，直接另存即可
- 如果是**非零值**（比如 `0x1A2`）→ 把光标移到该处，选中从第 0 字节到该位置**之前**的全部内容，删掉

删完保存。

> 建议「另存为」一个新文件，别覆盖原文件。选错位置还能重来一次。

### 认文件头这件事，可以举一反三

这类题的核心就一句话：**找到文件真正的起点，把前面的杂质丢掉**。记住几个常见头部值，遇到任何"从流量里还原文件"的题都能套：

| 类型 | 文件头（十六进制） | ASCII 特征 |
|---|---|---|
| JPEG | `FF D8 FF` | —— |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `‰PNG` |
| GIF | `47 49 46 38` | `GIF8` |
| ZIP / docx / jar | `50 4B 03 04` | `PK..` |
| PDF | `25 50 44 46` | `%PDF` |
| RAR | `52 61 72 21` | `Rar!` |

## 六、结果

把多余字节删掉之后重新打开：

![修好的 111.jpg，双击已经能正常显示了](/img/httpcap-06.png)

图片完整还原，没有花屏、没有截断 —— 说明砍的位置刚好，`FF D8` 之后的数据一个字节都没伤到。

而且 EXIF 信息也完整保留着：手机型号 `Apple iPhone 16 Pro`、拍摄时间 `2026:11:10 16:29:25`。这两条能反证一件事 —— **拿到的是未经压缩的原图**，不是聊天窗口里那张缩略图。缩略图在重新编码时通常会丢掉大部分 EXIF。

![还原出来的原图](/img/httpcap-07.jpg)

## 小结

整个流程拆开看就是四步：**抓 → 筛 → 导 → 修**。

几个值得记下的点：

**一是"同一个热点"不是随口一提。** 抓包的位置决定了你能看到什么。流量不经过你的网卡，再强的工具也无能为力 —— 这也是为什么抓别人的流量，要么和他在同一局域网，要么得能控制网关。

**二是 HTTP 明文比协议特征更好认。** 老教程常教人用 `oicq` 之类的协议名过滤，新版 QQ 早就不走那套协议了，什么都筛不出来。反而是 `http` + 看 Info 列的类型标注，稳得多 —— 因为 `Content-Type` 是服务器自己声明的，藏不住。

**三是"追踪流"存的是流，不是文件。** 这是新手最容易困惑的地方：明明保存成功了，为什么打不开？因为流里混着协议头。理解这一点，后面所有"从流量还原文件"的题都是同一个套路。

**最后一点，也是这件事真正的意义**：一条明文 HTTP 连接，在同一个局域网里的任何一台机器上，都能被完整拆开、还原、查看。图片、网页、表单、Cookie，一样都藏不住。

这也正是现在几乎所有站点都上了 HTTPS 的原因 —— 不是为了防什么"专业黑客"，而是因为**在不加密的链路上，旁观是一件零成本的事**。
